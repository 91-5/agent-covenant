# ADR-0001: Demote §6.6 (acceptance cross-reference) from policy to advisory

- **Status:** accepted
- **Date:** 2026-09-29
- **Author:** 15812
- **Affects:** `PROTOCOL.md` §6, `tools/gate.py`, `templates/TASK.md`
- **Triggered by:** REVIEW-XJ-20260929-001, condition 1

## Context

`PROTOCOL.md` §6 listed six policy points and ended with:

> 6. every `Acceptance` id in the task card appears in `evidence`

`tools/gate.py` implemented five. Point 6 is not implemented, and cannot be
without a change of substance: the acceptance bullets in `templates/TASK.md` are
free-form statements ("`pytest` exits 0"), with no machine-readable ids to
cross-reference. An external reviewer read both files, counted, and caught the gap.

This is the exact failure class this project exists to prevent. A specification
that promises more than the checker delivers is a marketing document, and a team
that discovers it during an incident learns not to trust the rest of the spec.

We had two options:

1. **Implement it.** Add a `--task-card` parameter, define an acceptance-id
   convention (`A1`, `A2`, …) in the card schema, and update every template,
   example and existing verdict.
2. **Admit it and demote it.**

## Decision

> We will **demote §6.6 to advisory** in v0.1, state the gap explicitly in
> `PROTOCOL.md` §6 and §10.5, and record the implementation as roadmap work
> behind a defined acceptance-id convention.

The mapping from acceptance criteria to evidence is the reviewer's job, performed
by hand, until the card schema carries ids. `gate.py` checks that *some* evidence
exists; it does not check that it covers your criteria, and the protocol now says
so where a reader will trip over it.

## Consequences

**Accepted costs**

- The strongest end-to-end guarantee we can offer ("every criterion was checked")
  is not machine-enforced in v0.1. A reviewer can cite evidence that covers only
  some bullets and nothing will stop them.
- Introducing acceptance ids later is a schema migration for existing cards. That
  cost is real and is why we did not rush it into v0.1.

**Gains**

- Spec and code agree again, and the disagreement is *documented* rather than
  merely removed. A reader can trust the policy list, because each item is
  something the gate does.
- We kept the reviewer's credibility with the project: the first external review
  found a real defect, and the defect was fixed rather than argued away.

## Alternatives considered

| Option | Why rejected |
|---|---|
| Implement §6.6 in v0.1 | Needs a schema change (acceptance ids) plus checker, templates, examples and migration. A rushed convention is worse than a documented gap. |
| Delete §6.6 silently | A spec that quietly drops requirements is how a project starts lying to itself. Demotion with a reason is the honest version. |
| Argue the check is "advisory in spirit" | The spec said "all must hold". The reviewer was right. |

## Revisit-trigger

> Re-open this decision when **any** of the following holds:
>
> 1. a team reaches L2 (gate in CI, unattended) and reports a criterion that was
>    silently skipped because no evidence covered it;
> 2. three or more adopters ask for machine-checked acceptance coverage;
> 3. the card schema changes for an unrelated reason (e.g. the
>    `OWNED_FILES_CONFLICT` rule turns out to need structured fields), at which
>    point adding acceptance ids is nearly free.
