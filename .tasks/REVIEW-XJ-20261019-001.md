## 五个对抗性 Review questions 裁定

**Q1（mtime 同粒度漏判）** —— 有效，残余风险已兜底。`link_card.py` 读前 stat、写前再 stat，守卫是 `st_mtime_ns != link_stat.st_mtime_ns OR st_size != link_stat.st_size`。我实测 NTFS 下同一粒度两次写 mtime_ticks 会变；即便落同粒度，**size 不同即拒**。漏判的真实后果 = last-write-wins 静默丢一个字段组——但该窗口极窄（两次 stat 之间须完成一次完整写且 size 恰好不变），代码注释已明说「a size change makes the refusal robust even if two writes land in the same coarse mtime tick」，concurrent 测试也故意用 size 变化兜底。接受。

**Q2（写出是否应保留 BOM）** —— 本期选「读 utf-8-sig 容忍 / 写无 BOM」是正确 canonical。本仓 verdicts/ 全目录 JSON 均无 BOM，link_card 写无 BOM 与自身风格 + 期 2 门禁对齐；deepfreeze 侧 PS5.1 带 BOM 是 PowerShell 历史行为，由本侧读容忍，两仓不必统一写入编码。对期 2 无隐含影响（期 2 读 link 时 BOM 至多是已被 utf-8-sig 处理的既有值）。

**Q3（verdict_sha256 装饰品风险）** —— 本期「记录不校验」可接受，但须路由。作者的「三句钉死」（锁原始字节不锁语义 / 重序列化哈希即变 / 期 2 前无机器消费者）已在 docstring + 双 README 三处一致落地，措辞诚实。若期 2 永不到来，字段确实会腐化——但那是期 2 排期问题，非本卡缺陷。**我裁定不让 lint 现在就校验它**：无消费者的字段校验 = 死代码（同 006/14-001 反死代码裁定），且校验语义要落在 gate.py（受保护资产 #5），本卡不该碰。路由见 C3：真实消费只能在 gate.py、须 `protected_assets_targeted` + sir 批准。

## 独立发现
