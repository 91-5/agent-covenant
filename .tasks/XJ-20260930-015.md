# TASK XJ-20260930-015: retire the coercion that manufactures the violation it claims to prevent

- **Author:** 15812 (Jarvis, opencode) · **Created:** 2026-10-01

## Context

Round 013 recorded a rejected option: the 012 reviewer had suggested clearing the residual
`templates/TASK.md` staleness with "a maintenance id that re-maps the file", and I refused,
because a round that maps a file it never changed attests freshness it did not earn, and once
such a round exists "re-map it next cycle" retires any staleness on demand — the laundering
channel `SUPERSEDED` exists to close, opened from the other side. The card concluded that the
real defect was that `artifacts.json` carries two incompatible duties, and deferred the split.

**The reasoning was right about the motive and wrong about the premise, and I checked it only
now.** 013 refused the explicit form. It did not notice that the lint rule was manufacturing the
implicit form every single round.

Three measurements, all at commit `d5410f0` with process CWD `D:\15812\projects\agent-covenant`:

1. **013's two commits never touched a README.** `0aec1f9` is `CHANGELOG.md` only (7 insertions,
   3 deletions). `39d3229` is `.tasks/XJ-20260930-013.md` plus `CHANGELOG.md`.
2. **013's map entry lists both anyway** — `README.md` and `README.zh-CN.md`, alongside the
   `CHANGELOG.md` and `PROTOCOL.md` it really did touch.
3. **The gate retired 001's README staleness on that entry.** Two `[SUPERSEDED]` lines name
   `XJ-20260930-013` as the round that "re-judged it later and holds the current claim" for
   `README.md` and `README.zh-CN.md`.

So the laundering I refused in the explicit form **already shipped, undetected, inside the round
that refused it.** The mechanism is `check_unmapped_claim_surface`
(`tools/lint_cards.py:367`): `current = ids[-1]`, and the newest round must list all three
`CLAIM_SURFACE_FILES` or the rule fires. A pure-ledger round cannot comply honestly, so it
complies dishonestly, and `gate.py:256`'s superseded check then treats the fiction as a signature.
The rule's enforcement is what produced the violation.

**The same coercion produced an honest entry one round later, which is why this stayed invisible.**
`f5deb9e` (round 014) genuinely edited `README.md` (110 changed lines) and `README.zh-CN.md`
(313 changed lines) to move the test count from 95 to 99, so listing them cost it nothing. 013 and
014 ran the same forced line and produced opposite results, differing only in whether the round
happened to have touched the files. A rule whose compliance is a function of coincidence is not
a check.

## The fix

Replace the round-identity comparison with a claim-holding comparison. A claim-surface file is
covered when some round that lists it holds a verdict that is **PASS** and was **signed at or
after the file's current mtime** — that is the round actually standing behind today's text. Failing
that, `UNMAPPED_CLAIM_SURFACE` fires as before.

Two properties fall out, and both are the point:

- **The coercion is gone.** A ledger-only round no longer has to name files it never read, so its
  map entry stops being a lie, so the gate stops treating the lie as a signature.
- **The check gets stronger where it was blind.** It previously accepted any listing by the newest
  id regardless of that verdict's status or age. It now rejects a listing whose verdict is not PASS
  (FAIL **and CONDITIONAL**), and rejects one whose verdict predates the file's current text — the
  two ways "listed" and "held the claim" come apart.

`CONDITIONAL` is rejected on purpose. It means the reviewer approved the round *with* recorded
reservations, so it never stood squarely behind the text it did not sign off on cleanly; a
CONDITIONAL listing retires the staleness warning without anyone having vouched for the bytes.
This round's own precedent says so: `XJ-20260929-001` is the only CONDITIONAL verdict on disk, and
`README.md` still warns under it. That is the intended reading, and a reviewer who reads
CONDITIONAL as sufficient should return FAIL.

Where a project has **no verdicts at all**, there is no signature to read, and the rule degrades to
the old newest-id comparison rather than inventing a baseline — the same scope discipline it
already applied to a project with no artifact map. This fallback is not decorative: it is what
keeps `test_mapping_from_an_old_round_does_not_count` (the drift case that motivated the rule in
the first place) meaningful. Those six verdict-less cases were written against the old semantics
and still describe the right behaviour, so they are kept as-is rather than rewritten — a rule
change that has to edit its own regression tests to go green is a rule change whose blast radius
was not understood first.

## Baseline to hold

Recorded so a reviewer can detect a silent behaviour change rather than take the new numbers on
trust.

**First attempt at this baseline was wrong, and the way it was wrong is the useful part.** The
card originally read "`tools/gate.py` is untouched, so this round's gate output must not move",
with `checked = 12, violations = 25, advisories = 37` measured at `d5410f0`. That invariant is
false. It confuses *the tool being unchanged* with *the output being unchanged*, and those come
apart the moment the round edits any mapped file — which this round is required to do. Measured
at the same commit with the same CWD and the same command, after editing only
`tools/lint_cards.py` and `tests/test_lint_cards.py`:

| | checked | violations | advisories |
|---|---|---|---|
| at `d5410f0`, before this round's edits | 12 | 25 | 37 |
| after editing the two lint files | 12 | 35 | 29 |

All ten new violations are `STALE_VERDICT` on those two files, one or two per round across
`XJ-20260929-001`, `-002`, `004`, `-005`, `-006`, `-007` — every round whose map lists either file.
No finding disappeared and no finding changed code. The cause is mtime: editing a file pushes its
mtime past every verdict that maps it, which is the freshness mechanism working, not a regression.
The six `SUPERSEDED` advisories those rounds lose is the same effect seen from the other side.

So the invariant that actually holds is narrower and checkable: **the set of findings changes
only in ways attributable to files this round edited.** Concretely, `tools/gate.py` and
`tests/test_gate.py` are byte-identical to `d5410f0` (`git diff HEAD --stat` over both paths is
empty), so no finding may change for any reason other than mtime on the two lint files. A
reviewer can verify this by diffing the `--json` output before and after and confirming every
added finding names `tools/lint_cards.py` or `tests/test_lint_cards.py`, and that no finding was
removed.

Claim-holder state for the three claim-surface files at `d5410f0`, CWD
`D:\15812\projects\agent-covenant`, using verdict timestamps against file mtimes:

| File | mtime (UTC) | Latest listing verdict | Holds the claim? |
|---|---|---|---|
| `README.md` | 2026-10-01T07:30:24.641404Z | 014 PASS @ 08:36:21.368940Z | yes |
| `README.zh-CN.md` | 2026-10-01T07:30:24.642417Z | 014 PASS @ 08:36:21.368940Z | yes |
| `CHANGELOG.md` | 2026-10-01T08:46:24.444199Z | 014 PASS @ 08:36:21.368940Z (stale) | **no** — 013's listing is FAIL |

`CHANGELOG.md` was already uncovered at `d5410f0`: the file was edited at 08:46 by the commit
recording 013's FAIL, after every existing verdict was signed, so nobody stood behind its current
text.

**This table stopped being true the moment this round began, and the rule tracked it exactly.**
Editing `README.md`, `README.zh-CN.md` and `CHANGELOG.md` for this round pushed their mtimes to
09:27–09:28, past 014's 08:36 signature, so 014's PASS no longer speaks for their new text. All
three now warn — correctly, since this round has produced no verdict yet and therefore no one holds
any of the three. That is the rule working, not a regression, and it is the same mtime mechanism
documented under "Baseline to hold". The claim surface goes quiet when 015's own PASS verdict lands
and its timestamp post-dates these edits; if it does not, the rule is broken.

## Review questions

0. **Is the premise right?** Card section "Context" claims 013's map entry retired 001's README
   staleness without editing them. Verify it independently: `git show --stat 0aec1f9`,
   `git show --stat 39d3229`, the `XJ-20260930-013` entry in `artifacts.json`, and the two
   `[SUPERSEDED]` lines the gate prints for `XJ-20260929-001`. If that chain does not hold, this
   round is fixing a problem that does not exist and should come back FAIL.
1. Does removing the coercion **weaken** anything that matters? Concretely: name a round that, under
   the new rule, retires a staleness it could not have retired under the old one. If you cannot,
   say so — that is the claim being made.
2. The verdict-less case stays silent, on the grounds that no data means no baseline to invent.
   Is that a loophole? A project could suppress this rule forever by never producing a verdict,
   which is the one thing this ledger exists to make hard.
3. Neither FAIL nor CONDITIONAL holds a claim, so an unconfirmed round leaves the claim surface
   uncovered and the rule keeps warning. Is that right, or does it create an incentive to over-claim
   a PASS? Read question 2's loophole alongside this one: a project that only ever emits CONDITIONAL
   gets the same permanent warning that a project that never emits anything gets the same permanent
   silence. The rule is quiet on never-verdict and loud on never-PASS, and I would like that asymmetry
   ruled on rather than assumed.
4. `docs/lint-rules.md` justified the newest-id comparison as "the only comparison that catches the
   real gap". If that was wrong for four rounds of production use, what else in the lint corpus is
   justified by a rationale that was never tested against a case it was supposed to catch?
5. This round is proposing the *smaller* of two available fixes and deferring the schema split. The
   013 reviewer can rule on whether deferral is principled or whether I am again declining a finding
   — the last time I refused a reviewer's suggestion on security grounds, the refusal was sound in
   motive and the premise underneath it turned out to be false. Is the deferral here any different?
