## Adversarial Answers (5 questions from task card)

### 1. Claim audit

**Strongest overclaim found:** `PROTOCOL.md §6` lists 6 normative policy points as the gate's default policy. Point 6 ("every Acceptance id in the task card appears in evidence") is **not implementable** by the current `gate.py` — it has no mechanism to read the task card. The README "What the gate enforces" table correctly lists 5 items (omitting point 6), but the PROTOCOL text presents all 6 as "must hold per required id." A reader of the spec would expect the gate to enforce 6; it enforces 5.

**README line 43:** "nobody has shipped a reputation" — this is an unverifiable ecosystem claim without a search date, methodology, or links. It's the kind of sentence that looks strong until someone finds a 3-star project you missed.

### 2. Adversarial gate

No input was found where `gate.py` returns 0 on a *genuinely broken* delivery — because gate.py by design only checks structural conformance (field presence, valid values, mtime ordering), not content quality. This is the stated ceiling (§10.3).

The closest "near-miss" attacks:
- `evidence: ["x"]` + `independent: true` → passes. Fix via condition #2.
- Empty artifact list in `artifacts.json` → freshness check silently skipped. Minor.
- mtime manipulation (`touch` backdated) → undetectable without content hash. Inherent to filesystem-based checks.

**No blocking-level bypass found.** The gate does what it claims to do (structural + freshness).

### 3. N1/N2 strictness

**ERROR is correct.** Rationale from PM-1: the failure was *silent* — a confident, detailed review of the wrong artifact, with no error. WARN would allow the collision to proceed unchecked (CI exits 0 on WARN-only findings). For a protocol whose entire value proposition is "make silent failures visible," having the most dangerous silent failure be a non-blocking warning is self-contradictory.

**What would break if BARE_TASK_NAME → WARN:**
- `lint_cards.py` exits 0 on a directory with bare `TASK-002.md` (unless `--strict`)
- CI pipeline sees green, deploys
- Second agent's `TASK-002` collides, review goes to wrong artifact
- Nothing errors. PM-1 recurs.

**What would break if NAMESPACE_MISSING → WARN:**
- Same, but at the filename level instead of the reference level
- Both rules exist because PM-1 had two contributing factors; relaxing either one reopens the window

### 4. Concurrency / lost update

**Not a cop-out, but incomplete.** The "full concurrent write" case (two agents `git commit` to the same file at the same instant) is genuinely not statically detectable — you need a runtime lock or orchestrator-level serialization. The PROTOCOL is honest about this.

**What IS partially checkable and not yet linted:**
- If task cards declare "files I own" (a new `## Owned files` section), the linter could detect two *active* cards claiming the same file. This is a static conflict check on declarations, not on runtime behavior.
- The current task card schema (§4.1) has "Deliverables" (what will exist) and "Constraints" (what must NOT be touched), but no explicit "I am the sole writer of these paths during this task" field.

**Recommendation:** add an optional `## Owned files` section to task cards; lint for conflicts among cards in `IN_PROGRESS` status. This addresses the "two agents own one file" case at the *planning* stage, before runtime.
