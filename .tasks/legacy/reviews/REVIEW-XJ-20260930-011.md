## Answers to review questions

**Q1 — Is the precondition tight enough? Construct the fourth laundering
case.** All four constructions from the REQUEST are closed, and pinned by
asserting tests rather than by prose: (1) verdict/blockers disagreement — the
bar calls `_check_blockers`, so a successor whose `verdict` says PASS while
`blockers: 1` cannot be a candidate at all; the door is closed upstream of
freshness. (2) id case/whitespace — map lookups are exact dict keys; `ac-001`
≠ `AC-001`, so a differently-cased twin cannot retire anything (and a twin
whose id matches exactly *is* the same id, which is correct). (3) path aliases —
exact-string matching means an alias simply fails to match and the older
verdict remains stale: strictly fail-closed. (4) successor chains — each
candidate is checked fresh on the file individually, so a chain cannot launder
through a stale middle link. The one remaining surface is the operator-visible
`--max-clock-skew` (and, transitively, `--json`/`--quiet`): raising the skew
re-opens the future-successor door by design. That is acceptable because it is
an explicit flag, not a default — but it is also the only place the rule's
safety is parameterised rather than structural, so it belongs in the README's
limitation list. It is not there. Recorded as A3.

**Q2 — Should a FAIL successor be allowed to retire?** **Yes, and the test
proves it does not launder.** `test_fail_successor_can_retire` (L472–489)
requires the predecessor and gets `EXIT_OK` with `SUPERSEDED` printed, then
requires the successor and gets `EXIT_VIOLATION` with `VERDICT_FAIL` — the later
round is simultaneously the current authority on the file and blocked on its
own verdict. Forbidding it would create the opposite laundering: an early PASS
could not be superseded by a later "this got worse", which is exactly the
liveness failure the rule exists to cure. The `--require <old-id>` case is
handled correctly: the advisory fires and the run still exits 0, because the
requester asked about a claim that has since been replaced.

**Q3 — Is advisory defensible?** **Yes. The round-5 criticism — "a wrong
command was called a warning, and the card claimed it was fixed" — was about a
defect being mislabelled as an advisory.** This is the mirror case: a correct
retirement being labelled non-blocking, which preserves the audit trail (every
SUPERSEDED is printed, `--quiet` does not swallow it — `_emit` L1017) instead
of deleting history. §4.5's normative text (L146–167) backs it. The single
honest caveat is the one inside B1: it is called normative in the REQUEST's
deliverables but lives in §4.5, not §6, so the "§6 alone" promise fails.

**Q4 — Do 11 tests close the theme? What first?** **They close the four named
escapes plus the laundering-shaped FAIL case; the first addition should be a
successor-chain test** (A retired by B fresh at time T1, B retired by C fresh at
T2, requiring A must exit 0 with two advisories and requiring C must fail) —
it is the one composition the individual escape tests cannot see, and it is
the shape a future refactor of `_superseded_by` would most plausibly break.
A distant second: a fail-closed alias test (`./README.md` key in the successor
map must not retire `README.md`), which currently passes by construction of
exact matching but has no test pinning that it stays that way.

**Q5 — Is the scope proportionate, and is the rule discoverable from §6
alone?** Proportionate in code (131 lines in `gate.py`, 169 in tests, one
semantic change); **not discoverable from §6 alone** — the normative sentence
is in §4.5, and §6's policy list is untouched. That is a placement defect, not
a rule defect, and it is part of B1.

**Q6 — Does this need a dedicated lint rule against future weakening?**
**No — the escape tests are the rule.** Each member of the successor bar has a
test that goes red if the member is removed; weakening the bar is a test
failure, not a silent regression. If anything, the durable hardening is
one line in `docs/lint-rules.md` naming `_successor_candidates`'s bar
membership as deliberate, so a future refactor has a place to read the intent.
Roadmap-level, non-blocking.

  dependency; one clause there would make the disclosure complete.

## What this round got right

The rule is correct where correctness is expensive: the successor bar refuses
unusable evidence at the candidate stage (not after laundering), all four named
escapes are closed by asserting tests rather than described in prose, a FAIL
successor retires without laundering and is proven not to by a second require
in the same test, aliases fail closed, and both READMEs mirror the four
disclosure clauses in the right register. The supervisory instinct — pinning
the pre-fix code against the five tests before shipping — is exactly the
practice that caught the draft's two holes, and docstring evidence
("against the pre-version these FAIL") suggests it was actually done, though
the FAIL verdicts themselves are not on disk (A1). The failure is confined to
the ledger: counts that cannot be reproduced, a file listed as touched that
was not, and a normative clause placed where its own discoverability claim
says it is not. Fix the ledger, not the rule.
