## The eight review questions

### Q1 — Is `STALE_TEST_COUNT`'s ERROR severity earned, or authorial embarrassment?

**WARN is the letter of the law; ERROR is defensible but must be argued, not
asserted.** The severity philosophy says ERROR means "a machine reading this
directory would be misled". No machine reads a README count and acts on it;
the gate never opens the file. By that literal test, a stale README number is
a WARN — and every other "this smells" rule in the table agrees.

But ERROR is defensible on a different axis, which the current rationale in
`docs/lint-rules.md` actually gestures at: this number is the project making a
*claim about itself*, and the protocol's whole subject is claims about
deliverables that nothing re-checks. `VERDICT_WITHOUT_REVIEW` is a WARN even
though a machine gates on it; the severity table is already
deployment-dependent by design. A count that drifts for three releases (45 →
69 → 78 → 82) is not a cosmetic slip; it is the exact failure class,
occurring on the project's own front page.

**Judgement: keep ERROR, on the explicit grounds that the claim surface is
part of the deliverable and a self-directed false statement is the one lie a
verification protocol cannot tolerate.** What I would not accept is the
motive — the rationale must be the rule's, not the author's embarrassment.
The present wording ("ERROR, because the protocol is being asserted falsely
about itself") is close enough to that grounds; sharpen "asserted falsely"
to "a claim the project makes about its own deliverable" and it states the
real justification.

### Q2 — Should the linter import the test suite on every run?

**Yes — importing beats recording, and the recorded-count version is the
weaker option for a specific reason.** Discovery runs in-process in ~0.7s,
stdlib only, no subprocess, no environment assumptions (§5: the checker must
be executable). The alternative — a file the gate writes — introduces a
*second* claim surface that drifts exactly the way README counts did; you
would have built a machine to catch one drift and fed it a fresh source of
the same disease. The import risks (test-module side effects) are contained
here because the suite is stdlib-only and small. Keep the import; keep the
`top_level_dir` default, whose failure mode is now documented in the
docstring.

### Q3 — Should a failed discovery be a WARN instead of silence?

**Yes — say so loudly, because you already proved why.** The silent path
hid a real bug during implementation (`top_level_dir` made discovery refuse
a non-package `tests/`, so the rule was dead on this very repo until a test
caught it). This is PM-10 inverted one level down: there, a check shrank
because a flag was forgotten; here, a check switches itself off and returns
"nothing to compare". A verifier that reports success while silently
skipping its check is worse than no verifier — by the project's own
transferable lesson, the configuration gap must be loud. Emit a
`TEST_COUNT_UNVERIFIED` WARN ("suite discovery failed; count not checked")
when `_discover_test_count` returns `None` *because* an exception fired — as
distinct from a project that simply has no `tests/` directory, which is
legitimately nothing to compare. This is a recommendation for the fix
round, not a condition on this verdict: B1 already returns FAIL, and this
ships with it or not at all.

### Q4 — Is `UNMAPPED_CLAIM_SURFACE`'s opt-in (`--artifact-map`) the right call?

**Half right, and the other half is visible from your own README.** Opt-in
protects users with no `artifacts.json` from a rule that would invent a
baseline — that part is correct. But `README.md` line 12 teaches the cold
reader to run the linter *without* `--artifact-map`, so the person most
likely to need the check never gets it; only your CI does. That is the
"a check that only runs when a flag is remembered" failure, in miniature.
Default to `./artifacts.json` when the file exists (fail loudly only when
neither the flag nor the default file is present) and the gap closes without
breaking flagless projects. Ship with the B1 fix.

### Q5 — Is "CHANGELOG exempt from the count rule but required in the map" coherent?

**Coherent, and the split is not a convenience.** A changelog entry is a
dated assertion about a past release — "45 tests" under `[0.1.0]` is
*true history*, and re-counting it would force edits to evidence, the
behaviour this project exists to prevent (same argument as `legacy/`).
Requiring CHANGELOG in the artifact map is about *freshness of the whole
file* — if today's entry changes, the newest verdict covering it expires.
One rule about numbers, one rule about currency; they operate on different
time axes. No change.

### Q6 — Do the two new rules justify the README's "caught by a check" claim?

**Not as worded — the claim is the same overstatement, one level up, and B1
is the evidence.** The README says the new surface is "caught by a check
instead of by a careful reader". What is actually caught: a *number*
mismatch in a fenced block, and a *missing map entry* for the claim surface.
What survived this very round, inside a fenced block: a command naming a
file that does not exist — asserted removed, actually shipped. The honest
version is the version `PROTOCOL.md` §10 already models: state what the
tools check, then enumerate the shapes they do not (false commands, stale
flags, wrong paths). Narrow the README sentence to the two specific shapes;
that is F4, and it is the cheapest fix in this round.

### Q7 — Is "fenced code blocks only" the right boundary for the count rule?

**Correct, and the narrower alternative is not implementable at an
acceptable false-positive rate.** A number inside a copy-pasteable command
is a checked claim; a number in prose is unclassifiable without semantics —
an "asserts the current count" shape would need to distinguish today's count
from a description of a past count, which is exactly the distinction the
first draft failed at when it flagged the paragraph documenting the fix.
Crying wolf on your own documentation trains people to ignore the linter —
that is a PM this project has already paid for twice (BARE_TASK_NAME
scoping, REVIEW-REQUEST exemption). Fenced-only is the boundary where the
rule is honest. Keep it, and keep the CHANGELOG exemption that pairs with it.

### Q8 — Is gating only the newest id in CI the right trade-off?

**Right trade-off, correctly documented.** Gating all history yields 22
permanent `STALE_VERDICT` violations — the freshness check working correctly
against verdicts whose artifacts have since moved — plus round 1's
`CONDITIONAL_NOT_ALLOWED`. A permanently red build is not a check; it is
noise everyone learns to route around (the PM-10 family again). What CI
must assert is narrower and true: *the round being shipped is signed and
current*. The workflow comment says exactly this, including the
acknowledgement that a PR adding an unmapped artifact will fail until it is
reviewed — that is the intended sequence, stated rather than discovered.
The residual risk (a middle verdict rotting unnoticed) is real but belongs
to the humans: the card lifecycle archives consumed rounds, and the newest
verdict is the only one anyone should be citing. Keep newest-only.
