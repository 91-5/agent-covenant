## Context

XJ-20261024-003 实现方在交付单里诚实承认：**run-log 可被篡改**（工具层无密码学防线）。当前防线只有「协议 + 事后交叉核对」，这对第二轮的关键断言（"B 臂全程零执行"）不够硬——如果执行者事后补造假日志，没有任何东西能发现。

**F2 要解决的就是这个**：让一次研究运行的证据面（run-data / run-log / 产物）**在运行结束时被密封**，此后任何改动都可被检出。

这正是本项目自己的纪律在测评侧的落地——「主张要能被独立复核」，而复核的前提是**原始材料没被动过**。

## Deliverables

- **D1** · `tools/eval/seal_run.py`：运行目录密封工具
  - 输入：一个 run 目录（含 `run-data.json`、`run-log.json`、`products/`）
  - 输出：`seal.json`——每个文件的相对路径 + SHA-256 + 字节数，加 `sealed_at_utc`、`file_count`、`root_label`
  - 可选 `--move-to <dir>`：密封后将整个 run 目录复制到指定 custody 目录（默认不移动，只写 seal）
  - `--verify <run_dir>`：对照 `seal.json` 重算全部哈希，逐字节报告漂移（新增/删除/改动），退出码 0=一致 / 1=漂移 / 2=用法错误
  - 纯 stdlib，Py3.9 兼容；**不做签名**（无私钥设施），只做**可检出篡改**的哈希清单——边界要在 docstring 写清
- **D2** · `tests/test_seal_run.py`
  - 密封后 verify 通过；改动 1 字节 → verify 报该文件漂移；删文件 → 报缺失；新增文件 → 报未登记
  - seal.json 自身不入哈希清单（否则自指）；空目录 / 缺 run-data 的用法错误路径
- **D3** · `docs/eval-runner-protocol.md` 增补一节：§11 运行密封（何时密封、seal.json 交付 custody、第二轮 runbook 插入该步）
  - **只增不改**：§9 runbook 现有步骤保持原样，在末尾追加密封步骤
- **D4** · `artifacts.json` 登记
