## Context

This is the first round in this repository that changes a tool rather than prose.

Before shipping v0.1.8 I ran the full chain — every id in `artifacts.json`, no
`--require` — and it reported:

```
GATE: FAIL (41 violations across 8 checked)
```

Forty-one. On a repository with four passing verdicts, three failing ones, and eighty-four
green tests. And it was not going to improve: **every id from round 001 onward was
stale**, because `README.md` has been read by eight verdicts since the first round and
every subsequent fix to it outlasted all of them.

The rule is correct in isolation — a verdict older than the thing it judges should
block. Applied to a chain, it is a check whose result is constant, and a check that can
only ever fail carries no information. The project already has this exact complaint in
its own catalogue: `STALE_TEST_COUNT` exists because *"a count nobody re-checks is a
liability"*. A gate that can only ever fail is the same defect in a different hat.

Worse, the consequence lands on a reader. The README teaches
`python tools/gate.py --verdict-dir verdicts --artifact-map artifacts.json`. A newcomer
runs exactly that, gets 41 violations, and concludes the project is broken. It was not
gated by that command before; the command was teaching a result nobody could achieve.

## Deliverables

- `tools/gate.py` — **superseded freshness.** When an artifact is newer than the verdict
  that judged it, the gate looks for a later id in the artifact map that also lists that
  file *and is itself a valid, fresh authority on it*. If one exists, the finding becomes
  `SUPERSEDED` and does not block.
- `tools/gate.py` — `_successor_candidates` runs the real `_check_*` helpers against each
  candidate and drops any that block; `_superseded_by` additionally requires
  `mtime <= successor_ts <= now + max_clock_skew`.
- `tools/gate.py` — `SUPERSEDED` is **reported, never dropped**. It prints in human
  output, appears in a separate `advisories` array under `--json`, and the count of
  superseded findings is always printed. The `ok` flag and the exit code are computed
  from blocking findings only.
- `tests/test_gate.py` — `TestSupersededFreshness` (6 tests): supersession works; it is
  reported rather than dropped; a successor with **no verdict** retires nothing; a
  successor that **omits the file** retires nothing; an **equal-ts** pair cannot supersede
  each other; `--json` separates advisories from violations.
- `tests/test_gate.py` — `TestSuccessorMustEarnAuthority` (5 tests): a stale successor, a
  future-dated successor, a non-independent successor and an evidence-free successor all
  fail to retire; a FAIL successor *does* retire, and still blocks when checked directly.
  Confirmed to fail against the pre-fix `gate.py`.
- `PROTOCOL.md` §6, `README.md`, `README.zh-CN.md` — the rule and its guards.
- `CHANGELOG.md` — `[0.1.9]`.
- `artifacts.json` — new `XJ-20260930-011` key.

## Constraints

- **A successor must earn authority; a round without one cannot launder.** The first
  version of this rule accepted any later `ts` and shipped green with six tests.
  Independent review reproduced two escapes at `exit 0`:
  - **A successor that was itself stale retired its predecessor.** It judged an older
    copy of the file, so nobody had judged the current file. Full-chain still failed on
    the successor, but `--require <earlier-id>` passed with zero fresh coverage.
  - **An unchecked successor laundered.** The candidate scan read only file existence
    and a parsable `ts`. A successor stamped 30 days in the future retired everything —
    PM-9 reached through supersession instead of through its own timestamp.
    `independent: false` and `evidence: []` worked the same way.

  So a successor must have a verdict on disk, clear the same `_check_*` bar any checked
  id does, and be **fresh on that file** (`mtime <= ts <= now + skew`). A successor that
  is itself stale, or judged an older copy, retires nothing.
- **A FAIL or unacknowledged CONDITIONAL successor is still a valid authority.** It
  retires the earlier claim and blocks on its own verdict. Requiring `PASS` would be the
  wrong axis — it would stop a later round from saying "this is worse than you thought".
  There is a test asserting exactly this.
- **`SUPERSEDED` must be visible.** The project's own rule is that the strongest check
  must never vanish silently. Supersession relaxes a blocking rule, so it has to be more
  visible than the thing it relaxes, not less.
- **Stdlib only, no new dependencies**, and the gate must still run in a locked-down CI
  image. Nothing here adds a dependency.
- **No retro-fit.** The 004–010 maps are untouched; 006, 008 and 009 stay FAIL.
- **Do not retro-fit the historical verdicts.** The 8 remaining violations on this
  repository are real and must stay: three FAIL verdicts, one CONDITIONAL not passed
  through `--allow-conditional`, and the stale findings that have no reviewing successor
  because 010 and 011 have no verdicts yet. Do not "fix" them by editing old verdicts or
  by loosening the rule further.
- **Do not extend the rule to the other checks.** Independence, evidence, and
  timestamp plausibility are not superseded by anything. Only freshness has a natural
  successor, because only freshness is about a file that a later round can re-read.

## Review questions

1. Is the successor precondition now tight enough, or is there a fourth case that can
   launder? Note that this revision already answers a review of the first version:
   stale successor, future-dated successor, non-independent and evidence-free successors
   are all rejected, and a FAIL successor is deliberately allowed.
2. Is allowing a FAIL successor right? The argument is that it is the current authority
   and blocks on its own verdict. If you disagree, say which is worse — a file whose only
   fresh verdict says FAIL being reported as unreviewed, or an earlier PASS outliving it.
3. `SUPERSEDED` is an advisory, not a violation. Does that distinction hold up now that
   the relaxation is conditional on a fresh, valid authority? Or is it still structurally
   the same reasoning that made a wrong command "a warning" in round 5?
4. This round changes a tool, which the project has not done since v0.1. Is the change
   proportionate, and is eleven tests the right size for a rule this load-bearing?
5. Does the relaxed precondition deserve a dedicated lint rule of its own, so that a
   future edit cannot quietly weaken it?
