## Answers to review questions

**Q1 — Now that the disclosure names no specific values, can it survive a
literal read?** **Almost entirely, and the fix went the right way.** Instead of
deleting the falsifiable detail, v0.1.7 *incorporated* it: the disclosure now
states the reviewer "signs itself inconsistently across rounds (`ximo@agnes` on
the earlier ones, `ximo@agnes-ai` on later ones), and no tool here checks the
signature field" — verified true against all seven verdicts. A reader opening
`verdicts/` finds the sentence confirmed. The one surviving literal-read failure
is B1, and it is not in the disclosure at all — it is in the new getting-started
section, which is where this repo's phantom-path family has now appeared twice.

**Q2 — Walk the six steps from an empty directory: which hold?** **Five of six
hold; step 5 fails.** Steps 1–4 and 6 were verified directly: tools are
stdlib-only and standalone (import scan); `templates/TASK.md` exists;
`examples/deepfreeze-pilot/artifacts.json` exists; all flags in the step-6
commands exist in `--help` (`gate.py` has no `--dir`, as the author repaired);
exit-code semantics (0/1/2) match `PROTOCOL.md`. Step 5's only pointer to the
worked example — the sentence containing the demonstrable FAIL round this repo
keeps intact — resolves to nothing (B1). The author walked the commands and not
the paths; the path is what broke. The walk itself is the right practice and
should become a per-release habit (A3).

**Q3 — Do PM-12 and one README paragraph complete the theme, or does it need
PROTOCOL.md too?** **They complete it; expanding the surface would dilute it.**
The evidence self-attestation is disclosed at the same depth as independence:
what the gate checks (presence), what it cannot (veracity), and why the field is
still worth having ("a claim, not a receipt"). PROTOCOL §6 already carries the
compatible advisory ("Do not assume the gate has verified your acceptance
criteria — read the evidence"); duplicating it in a numbered §10.x subsection
would create the second hand-maintained surface that just caused A1's three-round
rot. One merging suggestion, non-blocking: PM-12 could close by noting that
`ts`, `independent` and `evidence` are three faces of the same limitation — the
verdict is self-attested at three fields — so the next disclosure round
inherits a named family rather than rediscovering members one at a time.

**Q4 — Is dropping hand-maintained version numbers an honesty improvement, or
just a different set of claims?** **An improvement, and the reason is stated in
the text itself.** The Status section now reads "This repository is gated. Every
release below has a reviewer verdict in `verdicts/`, and the current state of
that chain is whatever the newest verdict file says — read it rather than
trusting a version number typed in prose," and then explains *why*: the headers
"went stale for three consecutive rounds… always in the conservative direction,
which is exactly why they survived review." A claim that cannot rot replaced
four claims that rotted on schedule. Two notes: the "every release" sentence is
load-bearing and true (mapping table in Evidence), but its verification path is
invisible — verdict ids and release numbers do not share names, so a reader must
open each verdict's `artifact` string to confirm. It is currently true; making
it *self-evidently* true is A2. And the "read it rather than trusting prose"
instruction is now the strongest anti-rot sentence in the repo: it converts its
own verification into an action, not a promise.
