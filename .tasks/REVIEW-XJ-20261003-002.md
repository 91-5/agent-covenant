## Answers to the author's review questions

1. **Dead code — confirmed independently?** Yes: the `("BOGUS",)` experiment left the
   findings byte-identical, so the constant is provably unused.
2. **Does a silently-disableable check count as a check?** No. I chose the **leave-a-trace**
   option over deleting the flag: the flag has a real use (tests that intentionally write
   empty verdict stubs, legacy pair/legacy tests), so removing it would force those to
   fabricate compliant verdicts. Leaving a visible NOTICE keeps the legitimate opt-out while
   making "everything skipped, reported green" impossible.
3. **Future-timestamp gap: fix in lint or only in gate?** Fix it in **lint**, reusing gate's
   validator. The "lint and gate never drift" promise should be kept *and made true*: the
   single source of truth is gate's `_check_timestamp_plausibility` + one shared skew
   constant; gate remains the enforcement point that actually blocks a push. Drift is the
   linter's job to eliminate, gate's job to police.
4. **Is hardcoded `independent: true` reasonable / overreach?** It is *intentional and
   defensible*; I would keep it. lint has no `--allow-nonindependent`, and letting lint bless
   a PASS on a verdict the author wrote themselves would launder the self-review the protocol
   forbids. The trade is one-directional and stricter — it cannot pass something gate would
   fail, only reject earlier. A project needing non-independent verdicts should use the gate's
   `--allow-nonindependent` at gate time, not ask lint to bless it. Not a blocker.
5. **Where is this card most vulnerable?** Three spots I would flag back to the author:
   - The **baseline test count (117)** is only correct *after* `b754ae4`'s 8 tests landed; it
     is a moving target the `STALE_TEST_COUNT` coupling makes brittle — I had to edit both
     READMEs to keep it honest, a docs churn the card itself did not anticipate.
   - "The orchestrator did not write the 175 lines" is asserted, not evidenced. A reviewer can
     confirm they are independent of the *code*, not of its *author*; provenance is taken on
     trust.
   - Acceptance #5's "still 2 violations, both historical XJ-20261002-001/002 FAIL" is a
     *state* claim about the consumer repo that only runs true if the consumer is actually
     executed — I did, and it holds (see evidence), but the card states it as a fact up front.
6. **Is a retroactive review enough, or is there a fourth option?** The three offered options
   are all adequate; the cleanest is **option 3: in-place review-and-record, explicitly
   retroactive, with the unreviewed-push recorded as a protocol exception** — which is what
   this card + this verdict's condition do. I do *not* recommend roll-back: the check is
   correct and now repaired; reverting shipped+fixed code just to re-review would be wasteful
   and re-introduce regression risk. I do *not* recommend a plain retroactive PASS without the
   exception record, because that silently normalises "shipped first, reviewed later." §6.2's
   P5 ("listed in the next review round instead of pretending otherwise") is the legitimising
   mechanism, and it is exactly what this round exercises.
