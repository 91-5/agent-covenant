## Review questions

1. **P1 是不是把门槛抬得过高？** 严格读它的话，**每一次 push 都需要一份 verdict**，
   包括改个错别字的 docs 提交。协议会不会因此失去可用性？该不该给
   「未声明 required id 的提交」留出免评审通道，还是宁可一律严？
2. **P2 与 P5 加起来是不是在正当化「先合后评」？** 一个规则自己先违反自己，
   再把这件事写进规则条文。读者可能学到的结论是「先做再补评审是被接受的」。
   你会怎么改这段措辞，还是维持现状？
3. **P3 完全不可机检，那它的价值在哪？** 「评审 A 合并 A+B+C」靠人自觉。
   有没有可能用 artifact map 或某个 manifest 把它变成可检的？
4. **P4 越权了？** 「未经验证的数字是缺陷」是本协议的强主张，但协议的机器只能查
   声明面新鲜度，查不了「这个数字谁数的」。要不要把它降为「condition 而非 blocker」？
5. **§6.2 放在 §6「The gate」之内是否合适？** 它讲的是流程纪律，不是门禁契约本身。
   独立成 §7、把命名规则后移，可能比塞在 gate 段里更清楚。
6. **这条规则回溯性地判了本仓过去的 push 有罪吗？** 历史里有几笔是先落地后评审的。
   是否需要在 `postmortems.md` 补一条，说明本规则不追究既往？
7. `docs/lint-rules.md` 里我写「linter 读工作树，看不到 `origin/main`，所以这个检查
   不能放在 linter 里」——这个理由成立吗？有没有我没考虑到的替代做法
   （比如 pre-push hook 或 CI 步骤其实更合适）？
