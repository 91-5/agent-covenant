## Context

v0.1.3 passed the gate and is public at `github.com/91-5/agent-covenant`. I then
read the published result as a first-time visitor would, and found that the
README I had just certified makes three claims that are false, while the gate
that produced the certification was green throughout.

1. **`# 45 tests` / `（45 个单测）`.** The suite held 69 tests when v0.1.3 shipped,
   and holds 78 after this round. Nothing was wrong with the tests; the number in
   prose was simply never re-read after it was written. The gate was green
   *because* it only ever read `.tasks/`, not the files a visitor reads first.
2. **`Status: v0.1`.** The tag is v0.1.3.
3. **"This project is not gated yet."** It is. The round-4 verdict is PASS with
   zero blockers, and the repository is public. This is the worst of the three: a
   false statement that argues *against* the thing that actually happened.

No rule caught any of it. All three are prose, and prose was outside the
checked surface. That is the defect class this project exists to prevent, and it
landed on the project itself — so the fix is not a text edit alone:

- `STALE_TEST_COUNT` (ERROR) reads the declared count back and compares it with
  the suite, in-process, with no subprocess.
- `UNMAPPED_CLAIM_SURFACE` (WARN) checks that `README.md`, `README.zh-CN.md` and
  `CHANGELOG.md` are mapped by the **newest** id in `artifacts.json`. They were
  still listed in the v0.1.0 maps, so a "mapped anywhere" check would have stayed
  green throughout — the file was mapped, just never by a round recent enough to
  be reading today's text. That is the gap that made the drift invisible, and the
  rule compares against the newest id because that is the only comparison that
  catches it.

## Constraints

- **Do not retro-fit the claim surface into the 004/005 maps.** Adding README to
  a map that predates this change would assert that a reviewer read a file that
  did not yet exist in its current form. The maps are evidence; the correction is
  a *new* map, on a new card, signed by a new reviewer. This is the point of the
  project and it is not negotiable.
- **Do not weaken a check to make a claim true.** The three false statements are
  fixed by changing the text. `STALE_TEST_COUNT` is added precisely so that the
  next 69→78 drift cannot pass silently again.
- The count written into the READMEs is the number the suite holds when the gate
  last ran, not a number chosen in advance and back-fitted to the tests. The
  count is asserted *inside a fenced code block*, which is where a reader copies
  it from and where a stale number actually misleads.
- `STALE_TEST_COUNT` deliberately reads only fenced code blocks. A number inside
  a copy-pasteable command is a claim that must stay true; a number in prose is
  commentary. The narrower rule is the correct one — the first draft of this
  rule flagged the very paragraph documenting the fix, and a linter that cries
  wolf on its own documentation is one people learn to ignore.
- A changelog entry is history: a past "45 tests" is correct and must not be
  re-litigated. `CHANGELOG.md` is therefore exempt from the count rule while
  still being required in the artifact map.

## Review questions

1. **`STALE_TEST_COUNT` is an ERROR on prose.** Every other "this smells" rule in
   this table is a WARN, and the severity philosophy says ERROR means "a machine
   reading this directory would be misled". Does a stale test count in a README
   meet that bar, or am I inflating ERROR because I am embarrassed about shipping
   the wrong number? If it should be a WARN, say so — I would rather argue about
   the severity than keep a rule whose justification is authorial.
2. **The rule reads the suite, so the linter now imports the test suite.** It
   runs discovery in-process on every lint call (~0.5s) and silently returns
   "nothing to compare" if the tree is broken. Is a linter that imports your
   tests acceptable, or should it read a recorded count (a file the gate writes)
   and accept the recorded-count version as the weaker option?
3. **Silent degradation.** If `discover()` raises, `STALE_TEST_COUNT` goes quiet
   rather than reporting an error. That is deliberate — a broken test tree should
   not turn a lint run into a crash — but it means the rule can be off without
   anyone noticing. This exact silent path hid a bug during implementation
   (`top_level_dir` made discovery refuse to import a non-package `tests/`).
   Should a failed discovery be a WARN?
4. **`UNMAPPED_CLAIM_SURFACE` is off unless `--artifact-map` is passed.** The
   rule has no baseline of its own. But a check that only runs when a flag is
   remembered is a check that will be forgotten. Is opt-in the right call, or
   should the linter default to `./artifacts.json` when that file exists?
5. **`CHANGELOG.md` is exempt from the count rule but required in the map.**
   Is that a coherent split, or is "exempt from the count, still freshness-
   tracked" a distinction I invented to avoid a false positive?
6. **Self-consistency:** the three defects I am fixing are all "the gate was
   green while the published artifact was wrong". Does adding two rules to
   prevent exactly that justify the claim in the README that the surface is
   now checked — or is that claim the same overstatement, one level up?
7. **`STALE_TEST_COUNT` reads fenced code blocks only.** A number in a
   copy-pasteable command is a claim; a number in prose is commentary, so the
   first draft — which scanned everything — flagged the very paragraph
   documenting the fix. Is "fenced only" the right boundary, or should prose
   counts be checked with a narrower shape, e.g. only a line that *asserts* the
   current count rather than describing history?
8. **CI gates the newest id, not the whole history.** I did this because gating
   all four historical verdicts yields 22 violations permanently, and a check
   that can never pass is not a check. But it also means CI will not notice a
   verdict rotting in the middle of the history. Is newest-only the right
   trade-off, or should the history be checked with STALE explicitly exempted?
