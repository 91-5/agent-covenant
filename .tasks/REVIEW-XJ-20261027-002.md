## 2. 缺陷剖析（C1，本卡最重的发现）

**崩在哪：** `--report`（stage-1 盲态报告）的「失败样本附录」逐条渲染 `j.claim.source_line`（report.py L271）。密封判定由 `_SealedJudgement`/`_SealedClaim`（L54）承载，但 `_SealedClaim` 只 `self.text = ...`，**丢了 `source_line`**。只要密封包里有一条 E1/E2/E3（r3 有 78 条），附录渲染第一行就 `AttributeError`，整份 `--report` 无产出。

**blast radius（精确划界）：** 三条件同时成立才崩——`blind_report`（`--report`）+ 带失败行 + 密封包。
- `unblind_fragment`（`--unblind`，sir 实际取数路径）不渲染逐条失败附录 → **正常**，M1 −48.3% 三方一致；
- 旧包（现场重判，回退到真实 `ClaimJudgement`）→ **正常**；
- 所以 sir 侧数字链路未被破坏，**破坏的是「盲态报告正文生成」这条交付面**。

**归属与测试盲区根因：** 缺陷**根源在 001（cedeaff）引入的 `_SealedClaim`/`_SealedJudgement`**（当时只暴露 `.text`），002 卡 D2 把 `blind_report` 列为交付面（头部无条件写快照行）却未验证它，故在本卡验收范围内暴露。433 全绿 + 作者实测全过的原因：(a) 测试 fixture 包判定全 E4 → 失败样本附录为空 → 从不到 L271；(b) 作者 A1 篡改测试在 `check_product_seal`（附录渲染之前）就抛 ValueError → 也绕过了 L271。「未篡改 + 有失败行 + 密封包 + `--report`」这条组合无人测过。

**修复对症：** 密封 JSON 里 `claim.source_line` 字段**是存在的**（实测 =10），只是 wrapper 没读——纯一行可修。建议别只补一个字段（见 advisory A2）。

## 3. 对抗性裁定（卡内四问）

- **Q1 A3 不追到底对不对**：**认可**。三条腿都站得住：(a) 3/3 全 258 + 内部自洽，158 在现行代码上不可复现，改不可复现的代码等于在猜；(b) 护栏 `test_summary_matches_its_own_per_code_table` 已在位，下次真复发会当场变红留证；(c) 新包已密封，「同包跨时刻两种结果」这类缺陷面从源头关掉。附带 E2=81（当初 75）的现场重判漂移是意外收获，坐实了 §12.1 机制、强化了 001 D1 必要性。处置「不追到底 + 护栏 + 新包密封 + 文档留方法」是该缺陷类的正确收口，不是逃避。
- **Q2 产物封签只给密封包是否留缺口**：**不留缺口**。旧包走现场重判，判定每次都从当前磁盘产物算出，**判定与磁盘天然一致**，加封签没信息量、还误导「这包也被密封了」。旧包跑 `--report` 头部明示「无产物封签」，把「这里没有 A1 保护」讲清楚不静默。A1 真正该守的是密封包（判定冻结在打包时刻、之后产物可被改），封签正好补在需要的一侧。
- **Q3 篡改不给 `--allow-drift` 是否过严**：**不过严，语义上必须不给**。drift（仓库合法前进）与 tamper（包内产物字节被改）是**两类不同事件**：drift 下密封判定仍是「打包时刻真值」、只是与当前仓库不可比，故可显式放行 + 引用双数字；tamper 下密封判定直接**失效**（描述的是另一份产物），放行等于拿失效数字当有效引用。想实验「产物被改后判定会怎样」，正道是改副本包（评审方 A1 三态就是这么测的），对真包开逃生门会破坏 A1「篡改即硬停」的核心语义。
- **Q4 `product_sha256` 放 manifest 而非独立文件**：**认可**。manifest 是包内唯一自描述清单，读侧读一个文件即拿到 P码→文件名→哈希，语义内聚；120 项 / 12.6 KB 相对 334 KB 密封判定可忽略，不影响解盲流程；放独立文件反而多一份要对齐、多一个漂移面。取舍正确。
