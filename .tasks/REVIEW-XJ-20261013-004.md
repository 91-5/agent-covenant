## Design review **on the card's written intent only** (`[inferred]`, not load-bearing)

> These answer the card's Q1–Q4 *as a design*, from the prose in `XJ-20261013-004.md` + `gate.yml`. They are **not** an execution-verified judgement of shipped behavior (there is none), and they do **not** change the FAIL above. Per the EVO-20261010-006 evidence-grade discipline: a claim not backed by a run stays `[inferred]`.

**Q1 — "CI-same-sequence (latest round)" vs "full-directory gate": should the hook be stricter?**
**Keep the CI-same-sequence; do NOT self-invent a `--baseline` mechanism in this card.** Ruling: `gate.yml` already adjudicated the same question ("gating every historical verdict would be a permanently red build; assert the *round being shipped* is signed and current"). The hook's stated purpose is **zero drift from CI** — a local shadow of the exact same judge and same "newest id" scope. Inventing a stricter local `--baseline` (exclusion of historical STALE debt) would *break* that parity by making local and CI disagree, which is the anti-goal the card names. Whether a genuinely stricter full-directory gate is worth a *separate* mechanism is a design question for a new ADR/card, not a scope-creep into this one. `[inferred]` — verify against the shipped hook only after it exists.

**Q2 — `--no-verify` is bypassable; the card chose "deter + document" over "block." Accept the boundary?**
**Accept it, with one caveat.** Technically a pre-push hook *cannot* block `git push --no-verify` (git skips pre-push on `--no-verify`), so "block" is not an available outcome — the card's framing is correct. The "deter" layer (stderr message + explicit "this bypass is recorded in your shell history") is the maximum a hook can do and is the right choice. The "CI-side bypass detection" (scanning commit messages for `--no-verify` traces) the card mentions is rightly dismissed as basically infeasible. **Caveat / recorded-on-file:** the durable guarantee is that **CI still runs the full gate after the push** — the hook is *prevention*, CI is *audit*; the two are complementary and that complementarity is the actual protection, not the hook alone. Recommend the card make that "the real backstop is CI, not the hook" line explicit so a reader doesn't over-trust the local hook. `[inferred]`.

**Q3 — installer does not auto-install (Constraint 2); list install as a first-class quick-start step?**
**Keep it opt-in (do not make it a first-class blocking step), but add a one-line "opt-in" note.** Forcing global install in quick-start would contradict Constraint 2 ("装不装是各克隆的自由；本卡不合并不安装"). A one-line mention ("run `bash tools/install-hooks.sh` to opt into local gating") in the README dev section is enough discoverability without changing the default. This matches the card's own "developer section + install line" plan. `[inferred]`.

**Q4 — multi-ref push (e.g. `git push origin master feature/x`); per-line "any branch push → run gate" granularity; should we gate only refs arriving at master and pass feature branches?**
**The card's per-line "any branch → gate" is the safer default; keep it.** Rationale: the hook's whole point is *prevention*, and a false "pass" on a feature branch that later fast-forwards into master is the same lost-update class the protocol exists to stop. Gating "only refs arriving at master" would require the hook to reason about the *remote's* topologies (which ref points where), which the pre-push stdin does not reliably give you locally; that adds a correctness surface with no proportional benefit. The cost (a feature-branch push runs the gate once) is cheap and matches CI's `on: push branches [master]` *plus* `pull_request` behavior, so it is defensible. If push-latency on feature branches becomes a real complaint, *that* is the revisit-trigger for a "gate only master-bound refs" refinement — do it then, with evidence, not now. `[inferred]`.
