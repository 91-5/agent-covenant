### 本卡的事实基础（Orchestrator 实测，2026-11-13，`out/r11-blind-samples.json` 400 条 + `out/r11-reliability-rows.json` 400 行）

**F1 · 主轨无锚 E4 假支持已实测量化（不是理论风险）**

按**层语义**（`layer`）作真值、按 `main_level` 作主轨判定，R10_ANCHOR 层 240 条交叉表：

| 真值 | 主轨判定 | 条数 |
|---|---|---|
| TRUE（cmd_ok / ref_ok / goldset_text） | E4 | **90**（全部正确） |
| FALSE（anchor_miss / repro_fail / ref_missing / incomplete / no_evidence） | E0 | 30 |
| FALSE | E1 | 30 |
| FALSE | E2 | 60 |
| **FALSE** | **E4** | **30 ← 假支持** |

- **假支持 30/150 = 20.0%**（占全部「应不支持」样本）；**占 anchor_miss 层 30/30 = 100%**
- 逐例坐实（`T01-c01` 等 30 条）：claim 原文「任务 T01 的答案为 **Apache-2.0**」，证据 `cmd=python -c "print('MIT')"` → `out=MIT`。断言内容与证据**直接矛盾**，主轨仍判 E4。
- 机制：主轨锚点正则 `(?<![\w.\-])\d+(?![\w.\-])` 把 `Apache-2.0` 的 `2.0` 正确排除 → **提取到零锚点 → 走「无锚机械通过」→ E4**
- **这是 dp 所举极端案例的真实兑现，30 例**；按 dp 分级表 `FP_upper > 15%` → **判「高」级**

**F2 · `design_error_class` 不能作为 HOLDOUT 层真值源（语料有效性缺陷）**

- 全 400 条中 `design_error_class != NONE` 者 **133 条，全部在 HOLDOUT 层**（R10_ANCHOR 层 240 条全为 NONE）
- 对 133 条逐条机械核对（claim 引用的数值 / 反引号 token 是否出现在 `fixtures_workspace` 对应文件或 cmd 输出中）：**矛盾 0 条**
  - 59 条 cmd 型：命令输出**逐字等于** claim 声称的数值 → claim 为真
  - 59 条 ref 型：fixture 文件内容**包含** claim 声称的数值 → claim 为真
  - 15 条 ref 不在 `fixtures_workspace` 中（该 15 条主轨判非 E4，方向一致）
- 结论：**HOLDOUT 层「注入错误」实际未生效**（133/133 标签与 fixture 不一致），任何以 `design_error_class` 为真值的测量在该层**无效**
- 推论：`design_error_class` 只可用于 HOLDOUT 的**设计意图记录**，不可用于真值计算；本卡真值源必须以**层语义 + fixture 机械核对**建立

**F3 · 分层现状与主 R_main 的分母**

- R11 可比集 174、弃权 226（轮十一）；轮十三对齐后可比 118、一致 118
- 无锚 claim 70 条（ref_ok 48 + goldset_text 22）在独立侧判 `INSUFFICIENT_NO_ANCHOR` 弃权，**未映射布尔**
- 主 `R_main` 分母必须保持全量可比集不变（防刷分）；`R_main_anchored` 另出
