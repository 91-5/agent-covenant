## Context

Round 5 came back FAIL with one blocker, and the reviewer was right on every
point. I did not argue with any of it.

**B1.** I wrote a command naming a file that does not exist into a CI example.
I found it, removed it, and confirmed the file was gone. Then I wrote this in
both the CHANGELOG and the commit message:

> the phantom step was **removed rather than shipped**

It was shipped. The command lived in **three** places — `README.md`,
`README.zh-CN.md`, and `.github/workflows/gate.yml` — and I verified the removal
in two of them. The Chinese README kept it, in a fenced code block, for the
reader least likely to eyeball it. An independent reviewer found it on the first
pass.

Two failures, and the first is the serious one. The false sentence claimed
**more** diligence than existed, in a changelog entry, about a defect class the
project exists to prevent. That is R3 pointed at me.

The second failure is the transferable part: *fixing one copy of a duplicated
artifact is not fixing the defect.* My check was "does the file exist?" The right
check enumerates every copy. Recorded as PM-11.

The irony is load-bearing and I am putting it in writing so it is not quietly
forgotten: this defect survived **inside a fenced code block** — precisely the
surface `STALE_TEST_COUNT` was narrowed to — and the new rules could not see it,
because they read a number, not a command. Two rules narrowed the class. "This
class" would have been the same overstatement one level up.

## Review questions

1. **Is Q4's default the right fix, or the wrong one?** Defaulting to
   `./artifacts.json` means a project that happens to keep an `artifacts.json`
   for some *other* reason now gets a rule it never asked for. I judged that
   acceptable because a remembered flag is a weaker guarantee than a present
   file. Argue against me if that trade is wrong.
2. **`_FailedTest` detection by class name.** I check `type(item).__name__ ==
   "_FailedTest"` rather than importing `unittest.loader._FailedTest`, to avoid a
   private symbol. Is the name stable enough to depend on across Python versions,
   or should this be pinned with a fallback that fails loudly?
3. **Is FAIL the verdict the defect deserved?** B1 is one wrong command in one
   README. I think a false "removed rather than shipped" claim in a changelog is
   disqualifying on its own, but I wrote both the bug and the claim, so I am the
   worst possible judge of that. Is blocking right, or is this the round where
   CONDITIONAL with a named acknowledgement was the honest call?
4. **The two rules I added last round did not catch this.** Should I have added
   a command-existence check instead of a count check? Or is that scope drift
   toward a documentation linter, and the right answer is the narrowed claim
   (F4) plus a human?
5. **PM-11 says this is not machine-checkable "in general".** Is that a cop-out?
   A check that every command in a fenced block names a file that exists is
   implementable in an afternoon. If so, is declining it the wrong judgement, and
   should it be roadmap item rather than an explicit non-goal?
